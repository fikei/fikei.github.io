# PRD: Design System Validation Pipeline

**Version:** 1.0
**Date:** 2026-02-07
**Status:** Draft
**Dependencies:** [AI Widget System v5.0](../../infrastructure/technical-design/ai-widget-system.md), [Variant Audit PRD](../../playground/systemic/prd-variant-audit.md), [Widget Design System PRD](widget-design-system.md)

---

## Executive Summary

Boards generates AI-powered widgets using Claude Haiku, renders them through a client-side template engine, and displays them inside `w-shell` containers built from our design system. Today there is **no automated validation** that rendered widgets conform to the design system — and no mechanism to detect when design system changes break existing widgets. This PRD defines a validation pipeline that connects the Boards widget output to the Dissect QA tool, enabling continuous conformance checking, drift detection, and design system synchronization.

---

## Problem Statement

| Today | Target |
|-------|--------|
| Widget templates use design system classes by convention | Templates validated against canonical component inventory |
| Design system changes (tokens, components) have no downstream impact analysis | Changes trigger automated re-validation of all widget templates |
| Variant audit is manual (human right-clicks variants in widgets.html) | Automated audit populates stoplight status from validation results |
| No way to know if a widget renders correctly at all 15 sizes | Every template × size combination tested on every design system change |
| Widget HTML is generated by client-side JS — never inspected | Rendered HTML parsed and compared against allowed class/structure rules |

---

## Goals

1. **Catch breakage before users see it** — validate every widget template against the design system on every change to either side
2. **Keep the design system honest** — surface unused components, undocumented classes, and token drift
3. **Feed the QA tool** — Dissect's variant audit should reflect real validation results, not just manual opinions
4. **No new runtime dependencies** — validation runs at build/CI time, not in production

### Data Flow

```
Design system file changed (tokens.css, components.css, widgets.css)
    OR
Widget template changed (boards/index.html template functions)
    │
    ▼
GitHub Action triggers validation agent
    │
    ├─► Step 1: Build inventories
    │     Parse CSS → extract all .w-* classes, --* tokens
    │     Parse templates → extract all referenced classes
    │     Build matrix: 10 templates × 15 sizes = 150 combinations
    │
    ├─► Step 2: Render snapshots
    │     For each template × size:
    │       Generate sample HTML via template function
    │       Mount in headless DOM with design system CSS
    │       Capture rendered output
    │
    ├─► Step 3: Validate
    │     For each snapshot:
    │       ✓ All classes exist in design system?
    │       ✓ Structure follows w-shell > w-header + w-body + w-footer?
    │       ✓ Body modifier matches template? (e.g., list → w-body--list)
    │       ✓ No inline styles overriding tokens?
    │       ✓ Container query breakpoints work?
    │       ✓ Required atoms present? (w-text, w-badge for verdict)
    │
    ├─► Step 4: Report
    │     Write audit.json:
    │       [{ template, size, status, errors[], warnings[] }]
    │     Post GitHub Check with summary
    │     If errors: block PR merge
    │     If warnings: annotate PR
    │
    └─► Step 5: Sync to Dissect
          Import audit.json into Dissect QA view
          Map validation results to stoplight status:
            pass → green
            warning → yellow
            fail → red
          Update variant-audit localStorage or Supabase
```

## Core Features

### 1. Design System Inventory Parser

Reads `tokens.css`, `components.css`, and `widgets.css` and produces a structured manifest.

**Output: `design-system-manifest.json`**
```json
{
  "version": "2026-02-07T00:00:00Z",
  "tokens": {
    "colors": ["--bg", "--fg", "--fg-muted", "--color-success", "..."],
    "spacing": ["--space-1", "--space-2", "..."],
    "typography": ["--font-primary", "--text-xs", "..."]
  },
  "components": {
    "atoms": ["w-text", "w-badge", "w-bar", "w-icon", "w-img", "w-btn", "w-checkbox", "w-divider"],
    "molecules": ["w-headline", "w-tag-group", "w-stat", "w-row", "w-axis", "w-option", "w-section", "w-column"],
    "modifiers": {
      "w-text": ["--display", "--title", "--meta", "--value", "--label", "--note", "--prose"],
      "w-badge": ["--filled", "--accent", "--success", "--error"],
      "w-img": ["--wide", "--banner", "--thumb", "--card", "--hero"],
      "w-body": ["--verdict", "--list", "--spectrum", "--split", "--narrative", "--comparison", "--choices", "--checklist", "--suggestion", "--grouped"]
    }
  },
  "sizes": ["sm", "med", "wide", "banner", "tall", "lg", "xl", "pano", "col", "poster", "max", "cinema", "board", "wall", "full"],
  "containerBreakpoints": [180, 280, 400, 560]
}
```

**Implementation:** Static CSS parser (regex or PostCSS). No runtime dependency. Runs as a Node script or Deno script in CI.

### 2. Template Extractor

Extracts widget template functions from `boards/index.html` and produces renderable samples for each template × size combination.

**Templates to extract (from WIDGET_TEMPLATES):**
| Template | Body Modifier | Valid Sizes |
|----------|--------------|-------------|
| `verdict` | `w-body--verdict` | sm, med, lg |
| `list` | `w-body--list` | sm, med, tall, lg, wide |
| `spectrum` | `w-body--spectrum` | sm, med, lg |
| `split` | `w-body--split` | med, lg |
| `narrative` | `w-body--narrative` | med, tall, lg |
| `comparison` | `w-body--comparison` | med, lg |
| `choices` | `w-body--choices` | sm, med, lg |
| `checklist` | `w-body--checklist` | sm, tall, med, lg |
| `suggestion` | `w-body--suggestion` | sm, med, tall, lg |
| `grouped` | `w-body--grouped` | med, tall, lg |

**Sample data:** Each template gets a fixture with realistic sample data (3 items, 2 tags, etc.) so rendering produces representative HTML.

### 3. Validation Rules

| Rule | Severity | Description |
|------|----------|-------------|
| `unknown-class` | error | HTML contains a `w-*` class not in the manifest |
| `missing-shell` | error | Top-level element is not `.w-shell` |
| `missing-body-modifier` | error | Template expects `.w-body--list` but body has no modifier |
| `wrong-structure` | error | Shell children are not header/body/footer in order |
| `inline-token-override` | warning | Inline style overrides a design token (e.g., `color: red`) |
| `unused-component` | info | Design system class never used in any template |
| `deprecated-class` | warning | Class marked deprecated in manifest |
| `size-overflow` | warning | Content overflows shell at a given size |
| `missing-responsive` | info | Template doesn't adapt at container query breakpoints |

**`audit.json` — consumed by Dissect QA view and GitHub Action**


### 5. Dissect QA Integration

Dissect's `VariantAudit` class imports `audit.json` and maps results to stoplight status:

```javascript
// New method on VariantAudit class
importValidationReport(report) {
  report.results.forEach(result => {
    const name = result.template;
    const size = result.size;
    if (result.status === 'fail') {
      this.setFlag(name, size, true); // red — blocked
      this.setNote(name, size, result.errors.map(e => e.message).join('; '));
    } else if (result.status === 'warn') {
      this.setNote(name, size, result.warnings.map(w => w.message).join('; '));
      // yellow — to process
    }
    // pass → no entry (green by default)
  });
}
```

### 6. Design System Drift Detection

Compares the current manifest to the previous one and reports changes.

**Drift types:**
| Change | Impact | Action |
|--------|--------|--------|
| Token removed | Breaking | Fail CI if any template uses it |
| Token value changed | Non-breaking | Info annotation on PR |
| Component class removed | Breaking | Fail CI if any template uses it |
| New component added | Non-breaking | Flag as unused until adopted |
| Container breakpoint changed | Potentially breaking | Re-validate all templates |
| Modifier added | Non-breaking | Info annotation |

**Previous manifest** stored as `design-system-manifest.prev.json` committed to repo (or fetched from `main` branch during PR).

## Agent Design

### Do we need agents?

**Yes — one agent, two modes.**

The validation pipeline is stateless and deterministic (CSS in, report out). It doesn't need AI. But two concerns do:

1. **Interpreting results** — When a template breaks at a new size, the fix isn't always obvious. Should the template adapt, or should that size be blocked? An agent can look at the design intent and recommend.
2. **Design system evolution** — When adding new widget types or components, an agent can analyze the existing design system and suggest whether to extend it or compose from existing parts.

### Agent: Design System Validator

| Aspect | Detail |
|--------|--------|
| **Trigger** | GitHub Action on PR touching `design-system/`, `boards/index.html`, or widget config files |
| **Mode 1: CI Gate** | Deterministic. Runs inventory parser + template extractor + validator. No AI. Outputs audit.json. Posts GitHub Check. |
| **Mode 2: Advisory** | AI-assisted. When CI gate finds failures/warnings, Claude analyzes the delta and suggests fixes. Posts PR comment with specific code changes. |
| **Runtime** | GitHub Action (Node/Deno). No Supabase function needed. |
| **Cost** | Mode 1: free (no API calls). Mode 2: Claude Haiku per PR (~$0.01/run). |

### Agent Workflow

```
PR opened/updated
    │
    ├─► [Mode 1: CI Gate]
    │     Run validation (no AI)
    │     Post GitHub Check (pass/fail)
    │     Upload audit.json as artifact
    │     IF all pass → green check, done
    │     IF failures → continue to Mode 2
    │
    └─► [Mode 2: Advisory]
          Feed failures + design system manifest + template code to Claude
          Prompt: "Given these validation failures, suggest minimal fixes"
          Post PR comment with:
            - What broke and why
            - Suggested code changes (diff format)
            - Whether to fix the template or block the size
          Label PR: "design-system-review"
```

### Do we need a separate agent for Dissect?

**No.** Dissect consumes `audit.json` — it doesn't produce validation. The QA view is a viewer/editor for audit data, not a validator. The agent writes the data; Dissect displays it.

## Infrastructure

### What's needed

| Component | Exists? | Work Required |
|-----------|---------|---------------|
| CSS parser (tokens.css → manifest) | No | New script: `scripts/parse-design-system.js` |
| Template extractor (boards HTML → sample HTML) | No | New script: `scripts/extract-templates.js` |
| Validation engine (manifest + HTML → report) | No | New script: `scripts/validate-widgets.js` |
| GitHub Action workflow | Partial (`agent-automation.yml` exists) | Add validation job |
| Dissect audit.json import | No | Add `importValidationReport()` to `VariantAudit` class |
| Previous manifest storage | No | Commit `design-system-manifest.json` to repo |
| Headless DOM for rendering | No | Use `linkedom` or `jsdom` (Deno-compatible) |

### What's NOT needed

| Component | Why Not |
|-----------|---------|
| New Supabase function | Validation is a build step, not a runtime service |
| Database tables | Audit data stays in `audit.json` + localStorage |
| New API endpoints | Agent runs in CI, not as a web service |
| Browser automation (Playwright/Puppeteer) | `linkedom` is sufficient for DOM structure validation; visual regression testing is Phase 2 |

## Phased Delivery

### Phase 1: Inventory & Manifest (1 session)
- Build `parse-design-system.js`
- Generate `manifest.json` from current CSS
- Commit manifest to repo
- Validate manifest is complete (all tokens, components, sizes)

### Phase 2: Template Extraction & Validation (1-2 sessions)
- Build `extract-templates.js` to pull template functions from boards
- Create sample fixtures for each template
- Build `validate-widgets.js` with rule engine
- Run locally, verify against known issues

### Phase 3: CI Integration (1 session)
- Create `design-system-validation.yml` GitHub Action
- Post GitHub Check with audit summary
- Upload `audit.json` as artifact
- Drift detection against committed manifest

### Phase 4: Dissect Integration (1 session)
- Add `importValidationReport()` to `VariantAudit` class
- Add "Import from CI" button in QA toolbar
- Map validation results to stoplight status
- Display coverage stats in QA header

### Phase 5: AI Advisory (optional, 1 session)
- Add Mode 2 to GitHub Action
- Claude Haiku analyzes failures and suggests fixes
- Post PR comment with suggested diffs
